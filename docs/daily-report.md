실제로 9/9 사장님 테스트 결제 1건이 이렇게 멈춰 있었습니다(바로 재결제하신 2번째 건은 정상 완성).

**어떻게 고쳤나:** 한 부분이 끝났는데 고객이 8초 안에 돌아오지 않으면, **서버가 스스로 다음 부분을 이어 씁니다.** 고객이 화면을 보고 있으면 지금처럼 글이 실시간으로 올라가고, 닫았으면 서버가 끝까지 완성해 PDF 메일까지 보냅니다. 실패 시에는 멈추고(무한 반복 없음), 부분 수만큼만 이어집니다.
- 테스트 4개 추가, 전체 104개 통과 · 빌드 통과 · 프로덕션 배포 완료
- 파일: `lib/report-resume.ts`, `app/api/reports/[token]/stream/route.ts`

**실서버 검증:** **성공.** 21:25에 멈춰 있던 테스트 리포트에 6초만 접속했다가 끊었습니다(고객이 화면을 닫은 상황 재현). 이후 아무도 접속하지 않았는데 서버가 혼자 파트 3(21:25~21:28) → **4초 뒤 파트 4 자동 시작**(21:28~21:30) → **21:30 완성**(4/4파트, 13섹션, 25,233자)까지 마쳤습니다. 이 검증에 쓴 API 비용은 파트 2개분(약 $0.6)으로, 오늘 테스트 한도 1건 이내입니다.

### 🔥 오늘 오전의 핵심 성과 — 프리미엄 리포트 분량 61% 증가

**문제 발견**: 정통 심층사주(19,900원)를 실제로 만들어보니 14,290자밖에 안 나왔습니다.
12섹션을 한 번에 요구하면 **전 섹션이 목표의 50~76%**에 그쳤어요. 프롬프트에서 최소 자수를
40% 올려봤지만 결과는 그대로(14,352자 → 14,290자). 토큰 상한 문제가 아니라(40K 중 18.5K만 사용)
모델이 긴 출력을 끝까지 유지하지 못하는 구조적 한계였습니다.

**해결**: 리포트를 4단계로 나눠 순차 생성하도록 구조를 바꿨습니다.

| 구분 | 자수 | PDF |
|---|---|---|
| 기존 (단일 호출) | 14,290자 | 18페이지 |
| 2단 분할 | 20,302자 | 24페이지 |
| **4단 분할 (최종)** | **22,963자** | **26페이지** |

12개 섹션 전부 목표 분량을 충족했고, 대운 섹션은 1세~50세를 4,093자로 다룹니다.

**추가로 발견한 치명적 문제**: 단일 파트 생성이 5.9분 걸리는데 **Vercel 함수 제한은 5분**입니다.
그대로 뒀으면 프로덕션에서 프리미엄 리포트가 타임아웃으로 죽었을 거예요.
→ 요청 1회 = 파트 1개로 나눠 각 요청이 106~196초(제한의 65% 이하)에 끝나게 했습니다.
중간에 실패하거나 화면이 꺼져도 진행분이 저장돼 다음에 이어서 완성됩니다.

### 개인화 품질 게이트가 실제로 일했습니다

어제 만든 `scripts/check-quality.ts`가 **프롬프트 금지 규칙이 동의어로 우회되던 것**을 잡아냈어요.
"겉은 차분한데 속은 **열정**"을 막았더니 모델이 "속으로는 **화력** 있어요"로 빠져나갔더군요.
어휘가 아니라 **구조 자체를 금지**하도록 프롬프트를 다시 썼고, 그 이후 생성된 리포트는 전부 깨끗합니다.

리포트 간 유사도도 측정했는데 **0.10~0.16**으로 매우 낮습니다.
"남과 결과가 똑같다"가 이 시장의 최대 사망 지점인데, 그 위험이 수치로 방어되고 있다는 뜻이에요.
